# Magic Engine — 风险分级工程质量闸

状态：强制治理规则  
适用对象：Claude Code、Codex、所有代码审查 agent  
配套规则：GitHub Issue #964《PR review convergence and stop rules》

## 1. 目的

Magic Engine 不采用“一切改动都用最高强度验证”，也不回到“先快速写、出事再补”的模式。

统一原则：

> **高风险地基慢而稳，普通业务正常推进，UI 和原型继续快。**

质量成本必须与真实失败后果匹配。测试、mutation、审查和文档是为了降低客户、资金、安全、数据和上线风险，不是为了追求测试数量、零告警或形式上的完美。

## 2. 开工前先定风险级别

每个 Issue / PR 在设计或编码前必须声明一个级别，并写出判定理由。只要命中更高级别的一项，按更高级别执行；不得为了少做验证而降级。

> **自报只是下限。** 从 §10 起，PR 的最终级别由 `tools/ops-review-loop/src/risk.mjs` 按实际 diff 算出，自报级别只作为**下限**参与（两者取更高的一档）。自报 C 而 diff 碰了 migration，最终就是 A。

### A 级：关键基础设施 / 高风险

满足任一项即为 A 级：

- 鉴权、权限、租户隔离、跨客户数据边界；
- Kernel、Capability 执行、审批、幂等、并发、锁、状态机；
- 数据库 schema、migration、RLS、生产数据完整性；
- SSRF、凭据、密钥、重定向、外部网络安全边界；
- 付款、计费、预算、供应商花费；
- CMS 发布、广告投放、邮件/社媒发布等不可轻易撤回的外部副作用；
- 失败可能造成客户数据泄露、错误执行、重复收费、生产中断或不可逆损害。

### B 级：普通产品与业务逻辑

典型范围：

- 内部 API、读路径、报表、诊断、排序、筛选、转换逻辑；
- 已有边界内的功能扩展；
- 可恢复、可回滚，且不会直接触发资金、发布、安全或跨客户影响的改动。

### C 级：展示、内容与原型

典型范围：

- UI 文案、样式、布局、非关键交互；
- 内部演示、探索性原型、一次性分析；
- 不改变权限、数据写入、外部副作用或核心业务语义的改动。

## 3. 各级必做质量闸

| 质量活动 | A 级 | B 级 | C 级 |
|---|---|---|---|
| 开工前设计 | 威胁模型 / 并发或失败模型 / 接口契约 | 简短方案与验收条件 | 目标与截图/验收描述 |
| 单元测试 | 必须，覆盖允许与拒绝路径 | 必须覆盖核心分支 | 仅对有业务逻辑部分要求 |
| 集成测试 | 必须覆盖真实边界；安全连接等无法由 mock 证明的性质必须用隔离、无生产副作用的真实边界测试 | 1–2 条关键链路 | smoke 或人工验收即可 |
| 回归测试 | 必须 | 必须 | 视影响范围 |
| Mutation | 只做关键安全/状态/身份/并发判据；冻结 head 跑一次完整相关套件 | 默认不做；高价值判据可做少量 targeted probe | 不做 |
| Type / lint / build | 必须，按已知基线判断新增错误 | 必须 | build 或相关检查 |
| 人工审查 | 按 `CLAUDE.md` 大任务规则；安全核心加攻击验证 | 一次集中 review | 自审或一次轻量 review |
| 最终证据 | 冻结 head、测试、CI、未解决 blocker、限制 | 测试、build、review 结论 | 截图/smoke/build 结果 |

“全部 mock”不是 A 级边界测试的同义词。若关键主张是“实际 socket 使用了已验证 IP”“真实数据库锁住了行”或“TLS 仍校验证书”，测试必须越过被证明的那一层；同时必须保持隔离，不访问生产、不消费 provider 预算。

## 4. Scope 闸：防止质量工作变成过度开发

所有 agent 必须执行以下规则：

1. **只实现当前调用方需要的最小契约。** 当前只需要 GET，就不得顺手建设完整 Fetch 的 POST / HEAD / body / credential 语义。
2. **每新增一种通用能力，都必须对应当前验收条件或已批准调用方。** “以后可能用”不能成为扩大范围的理由。
3. **测试跟随风险，不跟随代码行数。** 不为简单 getter、静态清单或样式改动堆 mutation。
4. **发现可分离的架构前置时拆 PR。** 不把功能 PR 逐轮长成基础设施重构。
5. **既有欠账登记，不顺手清理。** 除非它直接阻塞当前正确性或安全性。
6. **代码通用性不得超过证据能力。** 无法证明的承诺必须缩小契约，不得用更多 mock 代替证明。

## 5. Review 收敛规则

严格执行 #964：

- Round 1：对冻结 diff 做一次完整集中审查，一次性列出当前可识别问题；
- Round 2：批量修复后的验证，只检查修复和修复引入的回归；
- 第三轮仅限 Build Control Room 明确授权的新增安全、数据完整性、部署兼容或跨客户风险；
- 没有第四轮逐条打补丁；仍有架构 blocker 时必须停止，选择拆分、重设计、独立前置 PR 或交 Product Owner 定范围；
- 机器人新评论只是输入，不自动授权继续修改；
- P3、样式、推测性加固和范围外既有欠账进入 backlog，不延长当前 PR。

审查目标是收敛到可决策状态，不是把“还能想到什么”全部塞进当前 PR。

## 6. 验证运行策略

开发过程中：

- 先跑受影响测试和少量 targeted mutation；
- 每个小编辑不得重跑数小时的完整 mutation；
- 修复测试记账、文件拆分或探针锚点后，先做精准自检。

收口时：

- 冻结 head；
- 在冻结 head 上跑一次对应级别要求的完整验证；
- 如果最终验证因真实代码或测试记账问题失败，修复后重跑；这不自动开启新架构 review；
- 报告真实基线，禁止把子集测试说成全仓测试，禁止把 OOM / crash 误报为零错误。

## 7. Agent 开工与交付模板

### 开工声明

```markdown
风险级别：A / B / C
判定理由：命中了哪些真实风险
最小范围：本次必须完成什么
明确不做：哪些通用化、重构或范围外欠账不进入本 PR
验证计划：本级别要求的测试、集成、mutation、review
停止条件：出现什么情况必须拆分或回到 Build Control Room
```

### 收口报告

```markdown
风险级别：A / B / C
冻结 head：<sha>
实际 diff：<文件与范围>
验收证据：<测试 / 集成 / mutation / build / CI>
未解决问题：<按 blocker / non-blocker 分类>
范围控制：<主动没有实现什么，以及原因>
状态：Draft / 未 merge / 未 deploy / 未执行 Capability
```

## 8. 快速判定例子

- connection-bound SSRF fetch：A 级。CIDR、DNS rebinding、逐跳绑定和隔离 socket 测试是必要质量；为当前 GET 调用方扩展完整 POST/HEAD 语义属于过度开发。
- Kernel 审批 migration：A 级。并发、身份、部署顺序、真实数据库语义需要强证据。
- 新增内部诊断报表筛选：B 级。核心单测 + 少量集成 + build + 一次 review 足够，默认不跑完整 mutation。
- 改 dashboard 卡片排版：C 级。smoke、截图和 build 足够，不启动安全级审查。

## 9. 最终责任

- Claude Code：实施负责人，开工前声明风险级别并控制范围；
- Codex：架构验收与 Build Control Room 裁决，检查风险级别是否准确、证据是否匹配，不把非 blocker 变成无限修补；
- Review agents：按指定级别集中审查，不故意留问题到下一轮；
- Product Owner：决定业务范围、优先级、风险接受度，以及 merge / migration apply / 生产执行等不可逆动作。

任何质量闸都不构成 merge、部署、生产抓取、provider 调用或 Capability 执行授权。

## 10. 自动定级与交付评分（本节所述模块已在仓库中，尚未接入工作流）

§1–§9 定义了 A/B/C **是什么**，但没有定义**谁来判**。此前的答案是「写这个 PR 的 agent 自己判」—— 也就是让被约束的一方给自己打分。本节把判定变成确定性代码。

**当前状态（重要，别把它当成已生效）**：以下四个模块已经落在 `tools/ops-review-loop/src/`，有 150 条离线单测覆盖，但**还没有任何工作流调用它们**。接线是下一个独立 PR 的事。在那之前，A/B/C 仍由人按 §2 判定。

### 10.1 定级：`risk.mjs`

- 输入是 PR 的**实际改动文件清单**，不是 PR 描述。
- 命中受保护路径清单中任意一条即为 **A**（migration / `.sql`、`.github/workflows/`、`tools/ops-review-loop/`、`tools/ai-orchestrator/`、`render.yaml`、`src/middleware.ts`、`src/lib/auth/`、`src/app/api/auth/`、`src/app/api/webhooks/`、RLS、隔离判定、`src/lib/kernel/`、`src/app/api/kernel/`、`src/lib/execution/`、计费 / 支付 / 额度、cron 注册与路由、对外发布器、对外发信、花费与发布 guardrail、SSRF 边界、凭证、`package.json` / `package-lock.json`）。
- **C 是白名单，不是兜底**：只有文档、样式、图片、纯测试文件命中低风险清单；一个 diff 里**每一个**文件都命中才算 C。没认出来的一律 **B**。
- **读不到就是 A**：清单拿不到、为空、某一项没有文件名 —— 全部按 A 处理并注明「读不到」。「我们没看」和「我们看了没问题」不许长得一样。
- 自报级别只作下限（见 §2 的提示）。

### 10.2 抽样：`sampling.mjs`

C 级不必每次都请 Codex，但也不能一次都不请。按 `(PR 号, head commit)` 做**稳定** 20% 抽样：同一个 commit 永远得到同一个答案，重跑工作流、重复投递事件、作者反复重试都改不了结果。用 FNV-1a 而不是随机数，正是为了这一点。A / B 一律必审；级别认不出来也按必审处理。

### 10.3 轮次上限：`maxRoundsForRisk`

替换现行的一刀切 3 轮：**C = 1 轮、B = 1 轮、A = 2 轮**。认不出的级别给**最小**预算，不给最大。

> 为什么改：2026-08-27 的 PR #1204 是一个纯文档 PR，在旧规则下连跑三轮自动返修，最后还是落到 NEEDS HUMAN REVIEW。

### 10.4 交付评分与硬门禁：`quality.mjs`

总分 100，五个维度：需求与验收 30 / 测试与构建证据 25 / 安全与隔离证据 20 / 复用与不重复建设 15 / 失败处理与观测 10。
门槛：**C ≥ 75、B ≥ 85、A ≥ 90**。

评分只接受**已登记的证据信号**（某条 check 的结论、PR 正文里存在的某一节、diff 里有没有配套测试）。没观察到的信号记 0，没有「差不多给点分」这条路；传一个表里没有的信号会直接报错，而不是被静默忽略 —— 编出来的证据不许买分。

**硬门禁高于总分**，以下任意一条成立就不许 Ready，哪怕 100 分：

- 必过 CI 未通过，或读不到 CI 状态；
- 当前 head 还有未解决的 Codex P0/P1/P2；
- 评级绑定的 commit 与当前 head 对不上；
- A 级缺少对应专项证据；
- 任何一项判定输入读不到。

`NEEDS_PRODUCT_DECISION` **不会**因为分低或流程卡住而自动产生 —— 技术死胡同是技术问题。只有调用方明确断言存在业务范围 / 钱 / 客户事实 / 风险接受问题时才会出现。

**Codex 不产出结构化质量字段。** 实测（PR #1204，2026-08-27，四个 head 各一次复审）原生 Codex GitHub App 输出的是 markdown 散文，不是 JSON。所以 `CODEX_QUALITY_FIELDS` 常量取值就是 `unavailable`，报告里必须照实说；Codex 对本判定的唯一贡献是「当前 head 还剩几条 P0/P1/P2」，而那是硬门禁，不是分数。

### 10.5 定级记录：`gate-marker.mjs`

定级结果写成一条隐藏标记，**同时绑定 base 和 head 两个 SHA**：

```text
<!-- me-dev-gate:{"v":1,"base":"<sha>","head":"<sha>","risk":"A","reasons":["..."]} -->
```

只绑 head，rebase 或合并 main 之后 diff 变了、标记还显得有效；只绑 base，本该重跑的那一次 push 反而躲过去了。两个都比对，才让「head 一动，旧评级 / 旧评分 / 旧 Codex 批准立即失效」成为一次比较，而不是一句口号。载荷里的 `<` 和 `>` 一律序列化成 JSON 的 `<` / `>` 转义，所以文件路径里就算带 `-->` 也关不掉这条注释。
