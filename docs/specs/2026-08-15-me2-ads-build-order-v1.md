## 1. 为什么需要这份文档

PM 的原问题是「ME 2.0 里 Meta 广告应该怎么开发」。审计回答了「现在是什么样」，SOP 回答了「人该怎么跑测试」，**但「引擎本身怎么建」一直只存在于对话里**。

## 2. 广告在七层里的位置

| WP00 七层 | 广告这边是什么 | 现状（审计实测） |
|---|---|---|
| **Agent**（§3.1 只推理） | 这个客户该投什么、哪句话值得试 | ✅ **已有，且已在用** —— 见 §4 的关键更正 |
| **Domain Module**（§3.2 出候选，不自我授权） | **广告模块**：看数据 → 判断谁在赢 → 开处方（再做 5 个这个角度 / 把钱挪去 B） | ❌ 不存在 |
| **Measurement**（§3.3 对不上就 `not_comparable`） | **广告测量**：回答「这两条广告到底能不能比」 | ❌ 不存在 —— **最大的洞，见 §5** |
| **Shared Capability**（§3.4 唯一能对外写） | 真的对 Meta 动手：建广告、改预算、暂停 | ⚠️ 存在，但**散在 5 个入口、全不受治理**（`AD-SEC-1`，其中 3 个已上线） |
| **Kernel**（§3.5 治权） | 谁批准的、能花多少、能不能撤回 | ⚠️ 代码在 main；**四张表已于 2026-08-17 落生产**（PO 授权，见 #993），但仍**零真实调用方、零 run** |
| **Attribution / Flywheel**（§3.6 **分析投影，不是执行权威**） | 这条广告有没有真的带来询盘 | ⚠️ 部分有；`AD-ATTR-1` 指出取数不按来源过滤 |
| **Operating Brief**（§3.7 现在该看什么） | 今天哪条该停、哪条等你点头 | ⚠️ 有雏形（`src/lib/pm-todo/`）；`AD-QUEUE-1` 指出审批队列会吞待办 |

> **角色归属待 #872 确认的两处**：
> 1. 广告模块归 `domain_module` —— 本文认为清楚，但它是新建组件，需按 WP00 §3.2 明确「产出的是候选、不是命令」；
> 2. 广告测量归 `measurement` 还是并入广告模块 —— 本文主张**独立**，理由见 §5。

## 3. 「预算模块」不该是一个模块

它被七层拆掉了，而且拆得有道理：

| 这件事 | 归谁 |
|---|---|
| 谁值得加钱 | Domain Module 的处方 |
| 能不能加、加多少封顶 | Kernel 的授权与成本上限 |
| 真的去改那个数字 | Shared Capability |
| 加了有没有用 | Attribution（**只读，没有权力**） |
| 该你看一眼 | Operating Brief |

🔴 **不要建一个独立的「预算模块」** —— 那会变成又一个谁都能调、没人管的改钱接口。**现在已经有五个这样的口子了**（`AD-SEC-1`），这正是要收拾的东西，不是要再加一个。

🔴 **跨战线的预算分配（这个月钱放 SEO 还是广告）属于 Goal 层，不属于广告层。** ME 的定位是以 Goal 为中心的生意指挥平台，广告只是消耗预算的一条战线；预算一旦挂进广告模块，就永远回答不了那个问题。

## 4. 关键更正：做对投放的那条路，不是 ME 的产品代码

审计初版写「投得对的那部分是人在 Ads Manager 里点出来的」—— **错的，已撤回**（更正的正式口径见 PR [#982](https://github.com/bigbigraydeng-maker/magic-engine/pull/982) / Issue #981 closeout，本文引用它，不另立说法）。

准确表述分两层，**不要合并成一句**：
- **Product Owner 口径**：这些广告是 **AI 通过浏览器操作 Ads Manager 创建**的，不是人手工逐项建的；
- **ME 账本能证明的**：只有「它们不是 ME 程序化建广告链路留下的 lineage」。**具体操作者是谁，现有账本独立证不了** —— 这是 PO 的说明，不是数据库或 Meta API 可核实的运行证据。

这改变三件事：

1. **决策层已经被真金白银验证过，不用重建。** broad + Advantage+ 是 AI 自己选的（按 PO 口径）。
2. **五张空表（`ad_creative_links` / `winner_structures` 等）不是「没人用闭环」**，是**用的那条路不经过 ME 的账本**。
3. **同一个系统现在有两条路，一条做对一条做错**：浏览器那条**开着** Advantage+ 受众；产品代码那条（`ad-publisher.ts:116`）**写死关掉**。

> 按 CLAUDE.md 铁律 3，浏览器自动化本就是允许的中间态，链条是
> 「UI 入口 → Graph API 直调 → 页面注入 → DevTools 自动化 → **沉淀成 ME 产品能力**」。
> **卡在最后一步。** 用 ME2 的话说：**那条路是一个还没被治理的 Shared Capability。**
> 所以广告的 ME2 化不是重做它，是**把它收进共享能力的边界，再接上 Kernel 的签字**。

⚠️ **由此得出一条排序硬约束**：`AD-ADV-1`（把 `advantage_audience` 默认值按打法分开）**必须排在把浏览器路径产品化之前**，否则 ME 一上线就会用产品代码推翻 AI 自己已验证的结论。

## 5. 真正的断点不在内容，也不在预算，在「谁赢了」

裂变链路是四段：**谁赢了 → 照着做新的 → 投出去 → 钱自动流向赢家**。

内容工厂解决了第 2 段。断在**第 1 段**，而且断得比看起来严重：

- `winner_structures` **0 行**，唯一写入口是人工填 Airtable 表单；
- `ad_creative_links` **0 行** —— 系统不知道哪条创意带来了客户；
- **系统明确拒绝宣称谁赢了，而且理由正当**：同一广告系列内 Meta **先预测谁会转化再分配展示**，把组内数据当对照组会得出反向结论（`src/lib/ads-strategy/ad-level-breakdown.ts` 头部注释，该模块因此「从不宣称谁赢了」）。

→ **内容工厂能出 8 个变体，但今天没有任何东西能告诉它上一轮哪个值得裂变。**
不解决这一段，工厂只会更快地产出无法排序的东西。

这就是本文主张**广告测量独立成 `measurement` 层**的理由：它要回答的是「能不能比」，而不是「谁更好」——
按 WP00 §3.3，对不上必须产出 `not_comparable`，**不许降级成一个能比的数字**。这个职责放进广告模块会被处方压力挤掉。

## 6. 建设顺序（每步有完成标志）

| 步 | 做什么 | 完成标志 |
|---|---|---|
| **0** | **把手术室围起来** —— 5 个写入口收编成 1 个共享能力；补齐首发前置（`AD-GEO-0` / `AD-SPEC-1` / `AD-GATE-1` / `AD-LOG-1` / `AD-QUEUE-1` / `AD-FACT-1`） | **只剩一个地方能对 Meta 动手，且每一刀都留痕** |
| **1** | **建广告测量** —— 让「能不能比」有答案 | 系统能说「这两条可以比 / 这两条不能比，因为条件不同」 |
| **2** | **建广告模块** —— 拿测量结论开处方，**含预算处方**；只出建议单 | 系统能说「建议把 60% 挪给角度 C」，且这句话有据可查 |
| **3** | **接 Kernel** —— 花钱、动在投广告必须先签字，有上限，能撤回 | **没签字，一分钱都动不了** |
| **4** | **归因回流** —— 只读 | 能说清某条动作有没有把询盘推上去 |

🔴 **第 4 步永远只读。** 按 WP00 §3.6，归因是分析投影不是执行权威 ——
**「归因说好就自动加预算」这类自动放大回路，本史诗不建。**

⚠️ **第 1 步不能跳。** 跳过它直接做第 2 步，处方就没有输入，只能靠人读广告名字。

## 7. 一条反直觉的：第一版预算逻辑是「把钱交出去」

审计实测：CTS 账户 26 个广告组里 **14 个是单帖 boost，单条 $2–$37**。每条帖子新开一整套 = 把 Meta 的自动分配能力废掉，钱被切成跑不出学习量的碎片。

**先把多条创意放进同一个广告组、让 Meta 去分**，再谈自己算预算 —— 要写的算法比想象中少得多。

⚠️ 归并口径见 `AD-FRAG-1`，注意它拆成两件事：**(a) 组织归并**（campaign 复用，低风险，但**不等于修好了 learning**）与 **(b) 真正的碎片化修复**（共享预算 + 广告级生命周期，会改掉 `boost-post` 现有的每次一份预算/排期契约，属新设计）。
