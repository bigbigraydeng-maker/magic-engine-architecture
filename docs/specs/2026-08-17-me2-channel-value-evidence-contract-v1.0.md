## 2. 触发这条契约的真实事故

2026-08-17，在为大瑞 IP 系列课取数时，从生产库得出过一条**错误结论**：「社媒不是客源，搜索才是」。

数据本身没错，错在只看了一个采集面。CTS Tours NZ，同一窗口 **2026-07-19 ~ 2026-08-16**：

| 采集面 | 看到的 Facebook | 出处 |
|---|---|---|
| 网站侧（GA4 `ga4_traffic_snapshots.top_sources`） | **50 次会话**，占全站 4.8% | 网站分析 |
| 平台侧（Meta `ad_daily_insights`） | **106 条客资 / 103 条对话**，15 天投放 $1,007.58，**$9.51 一条** | 广告后台 |

两个数字都是真的，**但它们不是同一批人**。表单广告（`CTS — Lead Form — Reborn`，$9.94/条）与私信广告的客人在 Meta 站内就完成了留资，**从不进入客户网站**，因此在 GA4 中结构上不可见。

按网站侧数字判断，正确动作是「砍掉 Facebook」；按合并后的事实，Facebook 是该客户**单条成本最低**的客资来源。

PM 2026-08-17 拍板的渠道分工口径：**Google 做口碑，Facebook 拿 leads。两条腿，不是二选一。**

## 3. 契约条款

### 3.1 采集面（CollectionSurface）是渠道类 Evidence 的必填身份

任何用于渠道价值判断的 Evidence，**必须**声明其采集面，至少区分：

- `website` —— 经由客户网站埋点采集（GA4 会话、转化事件、落地页行为）
- `platform` —— 经由投放平台采集，且**客人未进入客户网站**（站内表单客资、私信对话、平台内转化）
- `search_console` —— 搜索展现/点击（属 `website` 的上游，但采集身份独立）

采集面是 WP00 §3.3「采集身份」的一个维度，**不是**质量信号，不可用置信度替代。

### 3.2 跨采集面不许相加，不许直接比大小

**红线**：不同采集面的计数**不得相加**，也**不得**在未声明口径的情况下直接比较大小。

- 违例示例：`GA4 Facebook 会话 50` 与 `GA4 Google 会话 658` 比大小 → 结论「Facebook 不如 Google」。**错**，因为 Facebook 的客资主体不在 `website` 采集面上。
- 违例示例：`50 + 106 = 156「Facebook 总贡献」`。**错**，两批人，相加即重复计数。

要跨渠道比较，只有两条合法路径：
1. **同采集面内比较**，并在结论中显式标注采集面（「在网站侧，Google 会话是 Facebook 的 13 倍」）；
2. **归一到同一业务结果口径**（如「一条客资的成本」），且每个渠道的客资数**取其主采集面**，并记录各自来源。

### 3.3 采集面缺失或不全 → `not_comparable`

若某渠道**存在投放但缺该渠道平台侧证据**（例：有 Meta 广告花费，但没有 `ad_daily_insights` 客资数据），则该渠道的价值判断必须产出 `not_comparable`，**不许**退化为「只用网站侧数字」得出结论。

这是 WP00 §3.3 红线的直接继承：**不许降级成一个能比的数字。**

### 3.4 Finding 层的引用要求

任何形如「渠道 X 有效 / 无效 / 应加码 / 应削减」的 Finding，其 Evidence 引用**必须**覆盖该渠道**所有存在投放的采集面**。缺一个 → 该 Finding 不合法（WP00 §5.2：没有 Evidence 引用的 Finding 不许存在，ME2 侧强制）。

### 3.5 工具层的表述约束

任何只喂单一采集面数据的取数工具，其面向 Agent 的描述**不得**声称可用于判断「渠道是否真的带来生意」。必须在描述中写明其采集面边界。

> 反面样本（legacy，仅作参照，不要求整改）：`src/lib/agent-tools/readonly/analytics.ts` 的工具描述为
> `Use this to check whether a channel actually drives business, not just rankings.`
> 而该工具只喂 GA4（`website` 采集面），结构上看不到 `platform` 侧客资。

## 4. 落地检查点

ME2 侧凡涉及渠道价值的模块，合并前必须过：

- [ ] 渠道类 Evidence 带 `collection_surface` 且为封闭枚举
- [ ] 存在跨采集面相加 / 直接比大小的**否定测试**（构造 GA4 低会话 + 平台侧高客资，断言不产出「该渠道无效」结论）
- [ ] 存在采集面缺失 → `not_comparable` 的测试，且**故意破坏一次**验证该测试真能失败
- [ ] 取数工具描述与其采集面边界一致

## 5. 对 legacy 的态度

`src/lib/zhuge/conductor.ts` 及其只读工具集 `src/lib/agent-tools/readonly/` 是 ME 1.0 遗留（`src/lib/action-bridge/index.ts` 已标注 legacy）。它每周一 03:00 由 `zhuge-weekly-recalculate` 触发。

### 5.1 🔴 更正：它的输出**有人消费**（2026-08-17 二次核实）

本文初稿据「`flywheel_actions` 无人消费」提议停掉该 cron，**该前提不成立，提议已撤回**（PR #1014 的停用 commit 已 revert）。

`persistZhugeActions`（`src/lib/zhuge/action-persister.ts`）写**三处**，不止一处：

| 写入 | 谁在读 | 数据活跃度（2026-08-17 实读） |
|---|---|---|
| `flywheel_actions` | 无已知消费方 | 324 条，近 30 天 154 |
| `zhuge_sessions` | `/api/clients/[id]/zhuge/latest-actions` → `ZhugePriorityWidget` → **客户详情页主界面** | 61 条，近 30 天 42 |
| `execution_items` | 执行看板 + 每日推荐（`lib/zhuge/daily-recommendation.ts`） | 1067 条，近 30 天 278 |

停掉调度会让**客户详情页上的优先建议无限期冻结在旧版本**，且不报错。

**教训**：判断「有没有人在看」时问了单张表，而生成端写了三张。**问『这个模块的输出有没有人看』之前，先把它所有的写入端点列全**，否则拿到的「没人看」是对错误问题的正确回答。

### 5.2 这让盲区问题更严重，不是更轻

原以为是「没人看的垃圾在烧钱」，实际是**有人看的建议基于有盲区的数据在排优先级**。客户详情页每周展示的优先建议，其判据结构上看不到平台侧客资（§2）。

据此：

- **不对 legacy 做整改**，本契约不构成对它的返工要求（ME2 方向，PM 2026-08-17）；
- 本文 §3.5 引用其工具描述仅作反面样本；
- **但停用它需要先迁移** —— 若将来要停，必须先把 `zhuge_sessions` / `execution_items` 两个仍被消费的输出迁到独立任务，不能直接摘调度；
- ME2 侧建成渠道相关模块时，§3 全部条款适用。

**遗留问题（未决，需 PM 决策）**：客户详情页当前展示的优先建议存在渠道盲区。是接受（等 ME2 重做）、还是给 legacy 打一个最小补丁（让它能看到平台侧客资），属产品决策。
